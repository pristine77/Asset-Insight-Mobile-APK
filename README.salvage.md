# Native Salvage workflow

The mobile workflow uses the backend's canonical Salvage report record. It does not infer report existence or processing status from generated file records.

1. Capture claim, Canadian market/date/loss details and up to 50 photos. Vehicle identity, engine and odometer controls are not in initial capture: include readable VIN/serial, engine-label and odometer photos and review extracted fields in the preview. New intake is CAD; blanks are unknown, not inferred from locale. Upload only after **Upload & prepare preview** is pressed. The same `details.client_submission_id` is retained across retries in the open form; a timeout or cancellation does not prove that the server rejected the upload.
2. An accepted `reportId` closes the capture form and opens the dedicated Salvage status page. The same report remains accessible from **Previews** and **My Reports** while processing, stopped, or after a failure. The page shows the canonical `workflow_steps` and progress; it never opens the editor automatically when processing completes.
3. Tap **Open preview** to review and edit the saved snapshot when `preview_available` permits it. **Close preview** returns to status, with an explicit discard warning for unsaved changes. `PATCH /salvage/:id/preview` sends `data` and `baseRevision`; saving does not upload photos. Server normalization owns repair totals. Media and comparable provenance are preserved by the backend.
4. **Save & submit** saves changes first, then submits using the returned revision and closes the editor back to persistent processing status. Previously submitted, approved, or declined reports use `/resubmit`. Revision conflicts keep local edits visible and require an explicit reload; mutation requests are not automatically replayed.
5. Accepted work is polled serially with a twenty-minute status window, bounded backoff, app/network reconnection and unmount cleanup. This status window allows for the backend's fifteen-minute research deadline plus queue/publication delay; refreshing resumes status checks, never paid work. Failure recovery uses `/salvage/:id/retry`, never a fresh report upload. Closing a status page does not cancel accepted server work.
6. File availability comes from canonical `downloadable` and `files` fields. The values in `files` are authenticated PdfReport IDs, not public storage URLs. PDF, DOCX, XLSX and images are downloaded through the existing `/reports/:id/download` transport with bearer/device context. Existing approval and release gates remain authoritative.
7. Assigned approvers inspect a read-only snapshot through `/reports/assigned-approvals/:PdfReportId/preview`, then return to Assigned Approvals to approve or request changes. This screen never calls the owner preview/edit routes for an assigned review.

The backend Salvage workflow endpoints must be deployed together with this mobile change. Source photo storage/public domains are not changed by the native workflow.

**Stop processing** is available only when the server exposes `can_cancel` and the current `job_id`. After confirmation it posts `{baseRevision, jobId}` to `/salvage/:id/cancel`; it does not merely stop polling. The editor remains closed until the server confirms that generation is no longer active. Old in-flight polling responses are fenced from overwriting the stop response. An uncertain response keeps editing locked while canonical status is checked. Stopped reports remain listed, and `/retry` with the current `baseRevision` resumes retained work under the same report ID. If no completed preview exists, only resume is offered; otherwise the owner may explicitly reopen, edit, and submit again, including stopping the next job independently. Closing a screen is never a server cancellation. Already dispatched external work may still complete or incur cost, but the backend must prevent stopped generations from publishing new files.

Customer-facing Salvage workflow, error, and limitation labels use neutral processing wording without provider/model branding. Evidence excerpts and supplied content remain unchanged; unknowns, incomplete results, automation and review requirements are not hidden or presented as human-verified conclusions.

V2 reports use the canonical assessment editor instead of the legacy financial editor. Saved pre-loss, repair, as-is and net-recovery values are read-only calculations. Parts, labour, charges, seller costs and appraiser overrides require source evidence or documented rationale; blank amounts remain null. Supplied records retain appraiser attribution. **Research again** requires confirmation and sends the saved revision plus an AsyncStorage-persisted logical request ID, reused after an unknown outcome. Ordinary saves never invoke it. New narrow-screen charts/report visual rollout and real-vehicle/device acceptance are still pending. The backend's authorized synthetic OCR/live-search smoke test passed on 2026-09-08; neither that smoke test nor mocked native tests establish production readiness.

Photo-derived vehicle details use the optional, server-owned `assessment.vehicleDetails` schema v1. Identity, engine/powertrain and workbook-specific fields are grouped in a responsive editor. The workbook supplies field definitions only. Unknown/conflicting readings show **Cannot find from image**, and rejected evidence remains reviewable. Image evidence expands on demand without duplicating uploads. Only `assessment_inputs.vehicleOverrides` is editable: strings are explicit user-entered values, `null` clears a value, and omitted keys preserve prior edits. Ordinary saves/file submission must not change evidence or trigger a new research run. Legacy assessments retain their prior editor with an image-provenance-unavailable notice. Deploy the backend contract before releasing this native update; existing reports are not automatically reanalyzed.

The optional server-owned `preview_data.report_enrichment` v1 projects saved summary, assignment/condition context, repair provenance, comparable/adjustment support, calculations, photo/evidence review, review checklist, revision history and final references into localized sections. Native displays those exact paragraphs and tables; it does not reconstruct financial or evidentiary conclusions. Sections expand on demand and wide tables scroll horizontally. An unsaved-edit notice distinguishes the last saved projection from current edits. Legacy reports without this object keep their existing preview.

**Appraiser report notes** are optional, preview-only `report_context` fields: intended use, scope of work, valuation premise, pre-loss condition, inspection basis, repair estimate status/date, lead times, market context, reconciliation notes, appraiser conclusion and client comments. Notes are labelled appraiser-authored, not verified findings or safety certifications. Text allows up to 6,000 characters; the optional estimate date uses `YYYY-MM-DD`. Editing one context field retains the others; null/empty clears it. The existing revision-checked save sends context but strips the read-only enrichment, media and assessment evidence. Saving requests no new research. Assigned review and active workflow locks keep notes read-only. Deploy this additive backend context/enrichment contract before the corresponding native release.

Verification: `npm test` and `npm run typecheck`. Focused service/component tests cover versioned vehicle edits, missing/conflicting readings, evidence/source preservation, enrichment rendering and context-only edits, submit/resubmit routing, conflicts, generation retry/poll disposal, protected downloads, and accepted upload handoff. These mocked tests are not a substitute for native emulator/device or real backend generation verification.
